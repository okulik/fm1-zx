# FM-1 ZX: a ZX Spectrum 48K firmware for the M-VAVE FM-1

**Status:** draft for the owner's approval, 2026-11-11.

## 1. Intent

Turn the M-VAVE FM-1 (a small synth) into a handheld ZX Spectrum 48K for **playing classic
games**. The FM-1's synth side is used only to play the Spectrum's own sound (the beeper). A
browser version comes with it: first a virtual FM-1 running the real firmware, then a plain
Spectrum emulator page built from the same core.

The approach: C on the device, Rust for the tools on the computer, JieLi's compiler in a
pinned Docker image, the community's felucca-bsp for the hardware, and fm1-emu to prove the
firmware before it goes near a real unit.

## 2. Goals, non-goals, anti-goals

**Goals (v1)**
- Boot into a game picker that lists the games built into the firmware; pick one and play it.
- Games run at the correct speed (50 frames a second, 69,888 T-states a frame) with correct
  beeper sound, including the border and beeper effects games rely on.
- **Smooth screen drawing matters to the owner:** the target is 50 display frames a second,
  including full-screen scrollers (see 5.4 for how, and what is proven where).
- The built-in set is **a few freely licensed games** that may be redistributed, so the
  repository, CI, public packages and the browser demo can all carry them.
- Each game has its own key mapping from the FM-1's controls to Spectrum keys or a Kempston
  joystick, with a sensible default.
- An update package (`.fwsc`) that the community installers take, and a documented way back to
  the stock firmware.
- A virtual FM-1 in the browser (fm1-emu) running the real firmware.
- Then: a plain browser Spectrum emulator from the same C core (computer keyboard, file
  drag-and-drop).

**Later (planned, not v1)**
- Uploading games to the FM-1 over USB from a browser page into its flash, replacing the
  built-in set without reflashing.

**Non-goals**
- Typing BASIC comfortably, 128K models, the AY chip, MIDI or synth features, save states,
  turbo/custom tape loaders, copy-protected loaders, timing-test demos.
- Any code or binary from M-VAVE's official firmware or SDK (`m-vave/fm1_open`,
  `libfm1_engine.a`). It was only read for reference.

**Anti-goals (a failure even if it technically works)**
- Games that run at the wrong speed, or sound that crackles or drifts.
- Controls that make games unplayable: a game whose keys can't be reached on the FM-1.
- A firmware that can leave the device in a state it can't be recovered from.

## 3. Constraints (from the hardware and community measurements)

- **CPU:** JieLi AC791N (package AC7911B8), two pi32v2 cores with a single-precision FPU.
  Custom firmwares that don't touch the PLL run at **360 MHz**; budget for 240 MHz until
  measured on hardware. Use only core 0 (some units misread memory on core 1).
- **Compiler:** only JieLi's pi32v2 clang 4.0.1 (`-target pi32v2 -mcpu=r3 -mfprev1`). No Rust or
  Zig on the device.
- **Memory:** about 512 KB SRAM, no PSRAM. A proven layout: RAMTEXT 48 KB (code run from SRAM),
  RAM 64 KB, POOL ~360 KB, NOINIT ~15 KB.
- **Flash:** 1 MiB total (P25Q80H), code runs from it (XIP) through a 32 KB I-cache. A cache miss
  costs **400-600 CPU cycles**, so hot code goes in RAMTEXT. The app slot is 581,564 bytes (0x8DFBC at XIP 0x02000120).
- **Misaligned access faults:** any misaligned 16- or 32-bit RAM access crashes the FM-1.
- **Calls between SRAM and XIP code** must go through a pointer (no long-call option).
- **Screen:** ST7789 240×240, RGB565 high byte first, over SPI1 with DMA. Existing firmwares run SPI1 at
  **12 MHz** (`LCD_BAUD` 4, 60 MHz / 5): a full 240×240 frame takes ~77 ms, about 13 frames a
  second. Faster dividers are untested on hardware.
- **Controls:** 14 buttons (OCT-, OCT+, FX, SCL, ENV, LFO, EDIT, GLO, HOME, SAVE, ARP, SEQ,
  PLAY, REC), 27 note keys (no velocity), 7 encoders, a MASTER pot (ADC), LEDs. Scanned at
  10 kHz by TIMER5.
- **Audio:** I2S (ALNK) to an external codec at 44,117.6 Hz (24 MHz / 544), block-based ISR.
- **Updates:** the community SysEx update protocol (felucca-bsp `chip/ota.c`) and Felucca's
  update loader, packaged with three files from JieLi's AC79 SDK (Apache-2.0). The device can be
  returned to the stock firmware through the community update path and M-VAVE's workbench.
- **Speed lesson from an earlier FM-1 CPU emulation:** a cycle-stepped CPU core (floooh `m6502.h`) cost
  ~90 pi32v2 instructions per emulated cycle; an instruction-stepped one ~9. A Z80 at 3.5 MHz
  needs an instruction-stepped core.
- **The device rule:** never flash the FM-1, send it SysEx or open its MIDI ports
  without the owner's explicit yes for that step; prove it in fm1-emu first.
- **No device yet:** the owner does not have an FM-1 at the start. Everything up to the first
  device test is proven in the host tests and fm1-emu; hardware-only facts (SPI speed, real
  cycle counts) wait for the device and are planned as the first thing done when it arrives.

## 4. Approaches considered

**Toolchain (the owner's decision):** C on the device, Rust for host tools.
felucca-bsp, not M-VAVE's code. Rust compiled to wasm and translated to C with wasm2c was
considered and rejected: an extra translation layer for no gain on the device.

**Z80 core:**

| Option | Trade-off |
|---|---|
| **redcode/Z80** (LGPL-3.0, ANSI C, ~3,000 lines + Zeta headers) | Most accurate (undocumented behaviour, MEMPTR, Q; passes Patrik Rak's, FUSE and other major suites), instruction-stepped, maintained. Callback-based (`fetch_opcode`, `fetch`, `read`, `write`, `in`, `out`, `hook`); speed on pi32v2 unknown. **Chosen by the owner.** |
| superzazu/z80 (MIT, one C file) | Smaller, passes zexdoc/zexall; less accurate, contention only per instruction. Fallback if redcode is too slow. |
| Own core | Full control over speed and layout; much more work. Only if neither fits. |

Rejected outright: floooh `z80.h` (cycle-stepped, ~10× too slow here), Fuse (a whole desktop
emulator), rustzx (Rust, can't run on the device).

**Game delivery (the owner's decision):** v1 builds a fixed set of games into the firmware
package; USB upload into flash comes later.

**Browser (the owner's decision):** both a virtual FM-1 (fm1-emu) and a plain Spectrum page;
the virtual FM-1 first.

## 5. The design

### 5.1 Repository layout

```
core/        C, shared by device, host and wasm: the 48K machine (memory, ULA, frame timing,
             screen decode, beeper, keyboard/Kempston ports, snapshot and tape loading)
third_party/ redcode/Z80 and Zeta, byte for byte, pinned, with their licences
platform/fm1/  device layer: crt0, linker script, main loop, LCD, input, audio, game picker,
             game pack reader; felucca-bsp vendored byte for byte in platform/fm1/bsp/
platform/web/  the plain browser page's C entry points (wasm)
host/        cargo workspace: tests, the game packer, the firmware packer, emu-gate
tools/       fm1-docker, docker/ (Dockerfile, toolchain hash), web-demo, wasm-core
web/         browser pages (virtual FM-1 overlay, plain emulator)
docs/        design notes, decisions, hardware test checklist
```

- **Licence:** GPL-3.0-or-later for the project (the builder's call made in conversation).
  redcode/Z80 is LGPL-3.0, felucca-bsp MPL-2.0, fm1-emu MIT: all compatible. Use REUSE/SPDX
  headers on every file.
- **Vendored code stays byte for byte:** hook around it, never fork it.

### 5.2 Build

- **Firmware:** CMake + Ninja with a `fm1` preset and `cmake/pi32v2.cmake`, run through
  `tools/fm1-docker` in a pinned `linux/amd64` image holding JieLi's Linux toolchain (pinned by
  SHA-256), CMake, Ninja, Rust and clang. The Dockerfile and `tools/fm1-docker` live in this
  repository; no image from another project is depended on.
- **Host:** `cargo test --workspace` compiles `core/` and the Z80 core with the `cc` crate and
  binds them with `bindgen`.
- **Package:** a Rust `fmzx-pack` builds the `.fwsc` from the app
  image, Felucca's loader and the AC79 SDK inputs (downloaded and checked by SHA-256), plus the
  game pack (5.6). The firmware needs its own product identity (`FM-1_<nnn>`); pick one that doesn't collide
  with known community firmwares (`FM-1_015` stock, `FM-1_900` and `FM-1_964` are taken).

### 5.3 Emulation core (`core/`)

- **Machine:** 48K Spectrum, 69,888 T-states a frame, interrupt at the frame start, ROM 16 KB +
  RAM 48 KB held in SRAM (copy the ROM from flash to RAM at boot: reads from XIP are slow). The
  standard 48K ROM is distributed with emulators by Amstrad's permission; record that in the
  licensing notes.
- **Accuracy target:** games run correctly; memory contention modelled well enough for timing-
  sensitive games (redcode's Z80InsnClock companion offers T-state precision if needed); border
  colour recorded per scanline; beeper edges recorded with their T-state.
- **Frame model (one frame of look-ahead):** the main loop runs one whole Spectrum frame,
  collecting beeper edges with T-state stamps and border changes per line; the audio ISR renders
  the previous frame's beeper edges into samples at those stamps. Pacing follows the audio
  clock: 44,117.6 / 50 ≈ 882.35 samples a frame (keep a fractional accumulator), so sound never
  drifts and games run at 50 Hz.
- **Beeper:** EAR/MIC output bits to a band-limited (or at least averaged-per-sample) square
  signal so it doesn't alias harshly; volume from the MASTER pot.
- **Input:** a 40-key Spectrum keyboard matrix (port 0xFE half-rows) and a Kempston port
  (0x1F), both driven from the per-game mapping.
- **Loading (builder's call made in conversation):** `.sna` and `.z80` snapshots, and standard-
  speed `.tap` through a ROM trap on the tape loading routine (redcode's `hook` callback), so
  multi-load games work. Turbo loaders are out.
- **Screen decode:** from Spectrum video RAM to RGB565 (or RGB444, see 5.4), with dirty tracking
  from the `write` callback on 0x4000-0x5AFF and the FLASH attribute's 16-frame toggle.
- **Same code everywhere:** `core/` builds unchanged for the device, the host tests and wasm.
  Host and device results must match (frame hashes).

### 5.4 Screen on the FM-1

- **Layout (the builder's call made in conversation):** the 256×192 picture is cropped to 240
  wide (8 px each side by default, with a per-game horizontal offset 0-16 px for games that put
  their score at an edge), no scaling. Vertically 240 - 192 = 48 rows remain: 24 rows of border
  above and below, drawn with the per-line border colour.
- **The SPI bottleneck.** The paper area is 240×192 = 46,080 pixels. Time for a full update
  (SPI1 clock = 60 MHz / (divider + 1)); 20 ms is one Spectrum frame:

  | Divider (clock) | RGB565 (16 bit) | RGB444 (12 bit) |
  |---|---|---|
  | 4 (12 MHz, today's) | 61 ms (~16 fps) | 46 ms (~21 fps) |
  | 2 (20 MHz) | 37 ms (~27 fps) | 28 ms (~36 fps) |
  | 1 (30 MHz) | 25 ms (~40 fps) | **18 ms (50 fps)** |

  The ST7789's datasheet write cycle (16 ns, ~62 MHz) allows divider 1; whether the FM-1's
  wiring does is unknown (existing firmwares all use 4).
- **How the 50 fps target is reached (the builder's call made in conversation):**
  1. **RGB444** (ST7789 colour mode 0x03): the Spectrum has 15 colours, so nothing is lost.
     Default.
  2. **Dirty lines:** send only the screen lines that changed this frame (from the `write`
     callback, the FLASH toggle and border changes). Most games touch a fraction of the screen.
  3. **Divider configurable at build time and at run time,** default 4 until the device test
     proves a faster one; aim for 1.
  4. **Graceful fallback when a frame's changes don't fit in 20 ms:** never slow the emulation.
     Send what fits, oldest-changed lines first, and carry the rest to the next frame, so a
     scroller degrades to a lower but steady rate instead of stuttering or tearing at random.
     (Interlacing alternate lines is an option the builder may measure against this.)
  5. DMA is asynchronous: the Z80 runs while a band is sent; double-buffer the line bands.
- **What is proven where:** fm1-emu proves the pipeline is correct (golden screens) and the CPU
  cost of the conversion. The SPI time is computed from the bytes sent per frame against the
  table above, and emu-gate reports **display frames per second for each test game at dividers
  4, 2 and 1**, so the screen performance is known before the device arrives. The real divider
  is set by the first device test (5.10).

### 5.5 Controls

- **Game picker:** shown at boot. An encoder scrolls the list, a key starts the game.
- **In game:** HOME opens a small overlay (resume, reset game, back to the picker, show the
  key map); PLAY pauses. Leaving a game discards its state (no save states in v1).
- **Mapping:** each FM-1 note key and spare button maps to one or more Spectrum keys or Kempston
  directions/fire, from the game's entry in the game pack. Encoders may map turns to key presses
  (left/right) for games that suit it. MASTER sets the volume.
- **Default mapping** for a game without one: Kempston on a gamepad-like cluster of note keys,
  with Space, Enter, 0-9 and Y/N reachable for menus and start screens.
- **Fallback on-screen keyboard (the builder's call made in conversation):** from the HOME
  overlay, a 40-key Spectrum keyboard picked with an encoder and pressed with a key, for name
  entry and rare keys.
- Which physical keys make the "gamepad cluster" is left to the builder after looking at the
  panel; check it on the virtual FM-1, then on the device.

### 5.6 Game pack (v1: built in)

- **The set (the owner's decision):** a few freely licensed games, committed with their licence
  texts and REUSE entries. The builder picks them and checks each licence allows
  redistribution in a firmware image and on a web page. The set should include at least one
  full-screen scroller (to test the screen fallback), one beeper-heavy game (sound timing), one
  game using border effects, and one multi-load `.tap` if a free one exists. Test-only material
  (CPU test suites) is fetched by SHA-256, not committed, where its licence requires.
- A manifest (TOML) lists the games: file, display name, key mapping, crop offset.
- A Rust tool converts each `.sna`/`.z80`/`.tap` into the pack format, compressed, and checks it
  by loading it in the host build of `core/`.
- The pack sits in flash after the app code, in the app slot. The builder decides whether it is
  linked into the image or placed by the packer at a fixed offset; the second is closer to the
  later USB upload path.
- **Budget:** firmware code + ROM is expected around 100-150 KB, leaving roughly 400 KB of the
  app slot, about 10-20 compressed games. The packer refuses a pack that doesn't fit.

### 5.7 Testing

- **Host (Rust):** the Z80 core against Patrik Rak's z80test and/or the SingleStepTests Z80
  data (redcode already passes them; this proves our build and callbacks); the 48K machine boots
  the ROM to its copyright screen (golden frame hash); snapshots and `.tap` loads reach a known
  frame after N frames; beeper rendering against reference samples; the game packer round-trips.
- **emu-gate (fm1-emu, pinned by git revision):** the firmware boots, shows the picker, starts a
  game and draws golden screens; key input reaches the Spectrum; **instruction budgets per frame
  and per audio block**; no misaligned access; RAMTEXT and flash sizes within budget.
- **Device:** a hardware test checklist (`docs/hardware-test.md`), each flash with
  the owner's yes.

### 5.8 First step: the speed spike

Before the rest, measure redcode/Z80 in fm1-emu with the real compiler: pi32v2 instructions
per Z80 T-state over a few game snapshots, code size, and whether its hot path fits in RAMTEXT.
The budget is one frame (20 ms) of Z80 at 240 MHz conservative (4.8 M instructions), minus
screen conversion, audio and input. If it doesn't fit comfortably, try superzazu/z80 next, then
an own core.

### 5.9 Browser

- **Virtual FM-1 (first):** a `tools/web-demo`: build and package the firmware,
  fetch fm1-emu at the pinned revision, run its web build, put our page (`web/`) on top, serve
  locally; deploy to GitHub Pages later. Risk: fm1-emu in the browser may not reach real time
  under the Spectrum's load; then it is a preview, not a way to play.
- **Plain Spectrum page (second; dropped by the owner on 2026-11-13):** `core/` + redcode/Z80 compiled with clang to `wasm32`
  (no libc, `rust-lld` linking), a canvas, the computer's
  keyboard, a WebAudio worklet for the beeper, drag-and-drop for `.tap`/`.z80`/`.sna`, and the
  same per-game mapping data so mappings can be tried here first. Later the USB upload page.

### 5.10 Milestones

1. Repository skeleton, Docker toolchain, host workspace; the speed spike (5.8).
2. `core/`: the 48K machine on the host, with tests.
3. Firmware: boot, LCD (RGB444, dirty lines, fallback, configurable divider), input, audio,
   picker, built-in games, packaging; emu-gate with the per-divider frame-rate report.
4. Virtual FM-1 in the browser.
5. ~~Plain browser emulator.~~ Dropped by the owner (2026-11-13).
6. **When the device arrives** (each flash with the owner's yes): first a small SPI test
   firmware that draws known patterns at dividers 4, 2, 1 (and 0) for the owner to check by eye;
   pick the fastest clean one. Then the real firmware, cycle measurements, tuning.
7. Later: USB game upload.

## 6. Decided by the owner

- C on the device; Rust for host tools; JieLi's compiler in Docker.
- felucca-bsp, not M-VAVE's code.
- Purpose: playing classic games; synth side only for the Spectrum's sound. **Revised 2026-11-13:** the synth side
  also plays games' beeper music re-synthesised as FM voices, as a menu choice (Plans 5-7,
  `2026-11-13-fm-music-design.md`).
- Games built in first, USB upload later.
- Browser: both, the virtual FM-1 first. **Revised 2026-11-13:** only the virtual FM-1; the plain
  Spectrum page is dropped. Moon Caves is dropped from the pack (uncleared third-party credits).
- Z80 core: redcode/Z80.
- The first firmware carries only a few freely licensed games. Plan 4 (2026-11-13) delivered four more (ZX Sopwith, Escape from Colony 8, ZX Dino, A World of One-Way) and two test programs; see `2026-11-13-more-games-design.md`.
- Smooth screen drawing is a priority; no FM-1 is available at the start.

## 7. Left to the builder

- Exact physical key assignments of the default mapping and the overlay.
- Game pack format and compression (a fast, small decoder: LZ4, ZX0 or similar).
- Whether the game pack is linked into the image or placed by the packer.
- Contention model detail, beeper filter, RGB565 vs RGB444, line-band size.
- Product identity string.
- Which test data sets to fetch and how (pinned by SHA-256, not committed if licences forbid).
